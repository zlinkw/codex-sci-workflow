# Explicit submission preparation

The full submission workflow triggers on “准备投稿 / 生成投稿包 / 投稿前检查”, not ordinary drafting, author acceptance or build. Final revised-manuscript delivery also loads the highlighting section below, without automatically triggering a submission package, backup or upload. Apply the kernel and current actual rules/state; no background export or external submission. Use [submission.py](../scripts/submission.py) only for a verified local LaTeX project and explicit dependency closure. The script does not establish scientific truth or journal compliance.

## Final revision highlighting

The author requires unified red highlighting at final revised-manuscript delivery, after the relevant revisions and author decisions are finished. Ordinary drafting and individual acceptance remain unchanged; finishing one review batch is not automatically final manuscript delivery.

- Compare the final accepted manuscript with the fixed original baseline agreed for this revision, preferably the actual submitted source. Record its verified identity in the existing profile/state and preserve it across review batches and cache compaction. Git is optional; neither a moving HEAD nor the latest candidate snapshot substitutes for the original. If the baseline is unknown or unavailable, ask for the intended source instead of guessing or claiming a complete comparison.
- Mark additions and the retained replacement wording red in the final deliverable's actual LaTeX source so that its normally compiled PDF shows the revisions. Keep unchanged content in its existing color; do not recolor an entire paragraph merely because one phrase changed. Ignore source line wrapping, comments, review metadata and equivalent formatting when identifying substantive revisions. Preserve reviewer-question classification colors and unrelated author marks.
- A pure deletion leaves no replacement text to color; identify it in the relevant reply, using a deletion display only if the actual venue/author requires one. Check changed equations, table cells, captions and figure assets individually with valid template-compatible markup. Do not wrap whole environments in a text-color macro, alter scientific figure colors to make them red or invent a picture change from a caption-only change.
- Read the response file's confirmed top-comment excerpt agreement. If excerpts are requested, insert the agreed passages from the final marked manuscript under their corresponding responses as part of this same final assembly, preserving exact wording, symbols and applicable red highlighting. If declined, add no manuscript excerpts. If the decision is missing, ask rather than silently choosing. Reconcile replies' change statements, excerpts and locations with this same final version. Check the compiled marked PDF for missed changes, excess coloring and formula/table/figure integrity, and verify page/line locators only against that version. Preserve existing metadata and the original baseline. No silent author acceptance, color removal, upload or plugin modification is authorized by highlighting alone.

Native review previews and optional legacy old-red/new-blue comparisons serve author review, not this delivery requirement. Reuse compatible existing red macros after checking their scope. The current submission helper and review plugin must not be described as automatically generating the final marked version unless their actual behavior has been verified. Delivery is incomplete if the required marked source/PDF or its baseline comparison is missing; report the specific remaining item.

## Submission package workflow

Before export:

For a medical-imaging AI reporting check, use the review skill's [CLAIM guide](../../sci-paper-review/references/claim-review.md). Verify whether the actual journal requires it; the 2024 checklist and its newer elaboration do not automatically impose a new TMI/MedIA submission requirement. Checklist coverage is separate from scientific sufficiency and does not authorize filling absent evidence or automatically changing source.

1. Reconcile all pending IDs, relevant open/awaiting-review annotations, stale replies, exact quotations/locators and the canonical scientific issue/evidence records. Unresolved items block readiness; never accept/reject/strip revisions just to produce a clean package. Source/code tests cannot establish issue closure.
2. Read the actual current venue instructions/template, article type, engine, root, bibliography style and submission requirements. Check title/abstract/length, anonymity if applicable, mandatory declarations, source/PDF/figure formats, references and any required .bbl. Unknown venue rules remain explicit gaps, not guessed defaults. Do not impose universal TMI/MedIA limits or run unrelated whole-paper rewrites.
3. Inspect main/includes, bibliography, class/style/font/figure/data dependencies and their literal/macro paths. Supply a minimal explicit file list; never recursively upload a workspace, .git, connection settings or credentials. Resolve external paths, generated inputs and missing dependencies before export. Static regex checks do not prove a full TeX dependency graph.
4. Verify scientific claims against real evidence, manuscript/reply consistency, citation metadata and rendered style. Use the corresponding narrow skill only for an actual outstanding task. Build/inspect a normal PDF of the exact source version, including formulas, cross-references, tables/figures and required page/line references. A synthetic compilation is not validation of a real manuscript.
5. Create/reuse a current [review backup](review-backup.md), preserving the internal audit chain locally. Record the actual checked-version identity in the existing state; no extra project Markdown tracker or new status table.

```text
python -X utf8 <skill>/scripts/submission.py preflight --repo <root> --state <owner.tex> --main <actual-root.tex> --files <explicit-source-assets> --git <git>
python -X utf8 <skill>/scripts/submission.py export --repo <root> --state <owner.tex> --main <actual-root.tex> --files <same-scope> --git <git> --destination <absent-output-outside-project> --checks <outside-project-checks.json> --latexmk <verified-latexmk> --engine <pdflatex-or-xelatex-or-lualatex>
```

When the verified venue requires a generated bibliography, add `--include-bbl` to export. The helper includes only the `.bbl` produced by that successful derived build, at its actual job-name filename in the ZIP, with its SHA256 in the report. Do not select generated build outputs or historical cleanup archives as source payloads, copy compiler output into the working manuscript just to export it, or broadly exempt hidden/private directories. A requested missing/empty `.bbl` or a differing explicitly selected `.bbl` blocks the ZIP rather than guessing or overwriting it.

`preflight` is read-only. Export requires evidence-bearing checks for `venue`, `scientific_evidence`, `reply_consistency`, `bibliography` and `visual_pdf`, each `{ "verified": true, "evidence": "actual source/PDF/version inspected and remaining boundary" }`. Not applicable items need a truthful reason. These are recorded attestations, not independent machine proof; do not fill true from a successful build or an unread source. Keep the checks JSON only with the derived artifact outside the paper, never as a live parallel tracker.

Export copies only the selected payload into an absent derived directory. It removes complete anchored CODEX comment blocks and CODEX pointer/locator lines **only in derived .tex files**, preserving scientific comments and executable content. Nested/unclosed blocks or executable content inside a block block export. Legacy revision syntax requires its explicit existing-mode resolution; removing colors is not author acceptance. Accepted final-red delivery formatting is not an unresolved review candidate and must remain in the marked export; a separate clean version does not replace the required marked version. The real manuscript, embedded state/rules, review refs and Git index remain intact.

The helper runs the selected local latexmk engine with shell escape disabled, retains full multi-pass build output, and creates `submission.zip` only after a successful derived build, an actual PDF and final engine log, no detected unresolved citation/reference warnings in that final log, and no concurrent source change. Expected first-pass warnings that later passes resolve are not final failures; never ignore an unsuccessful compiler exit or unresolved final warning. Compiler auxiliaries stay outside the source ZIP except the explicitly requested derived `.bbl` above; other venue-required generated assets need explicit supported handling. The derived PDF/report remain alongside the archive. A complex custom build needs its actual supported workflow, not a hidden engine substitution. Inspect the derived PDF and ZIP listing once; a passed literal-path check is not a security sandbox or a universal TeX parser. Report machine checks, scientific/editor checks, unchecked items and exact artifact paths separately. No upload, repository creation or new author decision is implied.
