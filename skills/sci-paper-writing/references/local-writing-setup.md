## Local writing setup and Git/GitHub

The writing toolchain is **VS Code + LaTeX Workshop + TinyTeX**. Git is optional backup only, never a prerequisite for writing, review, annotations, formatting or compilation. When configuring backup for an actual authorized paper, prefer local Git and a GitHub private repository and verify the first push. An unavailable remote affects backup completeness only. Reuse verified tools/repositories; global skill maintenance and tools-only work initialize/publish no real paper.

### Local editor and compiler

- Resolve the real current folder, existing VS Code profile/settings, independent document roots and child-file graph. Do not assume an historical paper path or pin the compiler to a filename such as `main.tex`. Use the active independently compilable document; for input/include children, resolve their real root. Preserve explicit project root comments where appropriate rather than silently rewriting them.
- Reuse TinyTeX/TeX Live and LaTeX Workshop. Match the project's engine, target template, TeX Live year and relevant dependencies; do not hardcode 2026 for every future project. Use `latexmk` to handle repeated engine runs and BibTeX/biber as actually required. Install only missing relevant packages after checking actual logs; a manager's zero exit code alone does not prove every package installed. Compare sample output when requested; do not promise byte-identical output to an unspecified cloud package snapshot.
- For a missing bibliography, inspect the first engine error before changing the recipe or bibliography data. A missing font or malformed class length can stop latexmk before BibTeX or the final reference-resolving passes. For example, `pcrr7t.tfm` belongs to Courier; verify the actual installed file after adding its package. Validate a successful complete build, resolved citations and the rendered reference list, not merely the presence of a PDF or `.bbl`. Never conceal errors with forced-success settings. When the author explicitly permits a reference template to compile without example assets, use clearly named placeholders only for missing files in that template; real manuscript figures remain required.
- Keep `Ctrl+S` as save then local build, `Ctrl+Alt+B` build, `Ctrl+Alt+V` right-hand PDF and `Ctrl+Alt+J` forward SyncTeX. The current local writing extension supplies Chinese build and forward-SyncTeX menu aliases; keep `latex-workshop.showContextMenu` false to avoid duplicate native entries. If the local bridge is unavailable, the Workshop setting is the supported fallback, not a second concurrent menu. Use PDF double-click for reverse SyncTeX and generate SyncTeX data. Discover installed command/setting schemas rather than patching an extension's package files to add a menu. See [local-latex-experience.md](local-latex-experience.md#supported-chinese-context-menus).
- Keep input/change/automatic-save compilation off by default; explicit save/build shortcuts trigger compilation. Do not initiate a compile merely because Codex changed prose. Keep auto-clean and failure-triggered cleanup off; preserve useful auxiliaries and observe the exact-path cleanup policy for any later cleanup. Put generated files in a per-document build directory such as `.latex-build/<document-name>` so separate manuscript/reply roots do not overwrite one another.
- Scope this workflow and editor commands to verified local LaTeX documents. Keep bibliography data and venue handling in sci-bibliography. Use the installed local compiler and preview; preserve existing manuscript paths and assets.
- Validate only the affected setup: JSON/schema/keybinding checks, representative compilation/bibliography and forward/reverse SyncTeX when compilation is authorized. Distinguish source/config validation, native SyncTeX checks and actual UI interaction; report a needed restart/reload or untested UI behavior honestly.
- For the author's approved editor experience, shortcuts, offline English checking, snippets, paste tools and manual formatting, read [local-latex-experience.md](local-latex-experience.md). It is the canonical operating guide; reuse installed configuration instead of appending duplicate settings. LaTeX is the only writing format; migration/removal of old formats and Zotero/external/realtime preview remain outside this setup.

### Conditional Git backup and remote history

- Inspect the actual project root, `git status`, repository top-level, branch, existing remotes and history before changes. Reuse an existing paper repository. Do not create a nested repository inside an unrelated ancestor repository, move the paper, rename a branch or retarget a remote silently. Do not infer a paper project from a global settings or skill directory.
- Only when configuring the author's requested Git backup for an unambiguous standalone paper project with no repository, the standing backup preference permits preparing a scoped `.gitignore` and initializing local Git after the source inventory and ownership checks. A new repository uses `master`; preserve an existing branch and resolve a conflicting upstream policy rather than renaming silently. Verify the Git author identity, inspect the exact initial file set and create a scoped first source commit. An initial commit records the existing state, not acceptance of unresolved revisions. Keep tools-only tasks repository-free unless the author names the paper project to initialize.
- Track manuscript/reply sources, `.bib`, class/style files, necessary fonts and original figure assets. Ignore .codex-review/, the actual build directory, verified transient compiler outputs and private connection/authentication state. Embedded review comments may contain private quotations/requirements; inspect the exact source export before any upload. Never blanket-ignore all `*.pdf`: paper figures can be PDF. Do not discard source assets or silently untrack existing files. Include submission-required generated files such as `.bbl` only through the actual venue/submission workflow, not a guessed universal rule.
- Before the first staging operation, merge the following minimum exclusions into the actual repository-root `.gitignore`, preserving existing rules. Unanchored directory patterns also cover child-document build/review folders. Add other generated paths only after identifying their producer and confirming they are not source assets. Keep this baseline here rather than depending on a separate template file:

  ```gitignore
  # Private review objects, request snapshots and derived review PDFs
  .codex-review/
  .latex-build/
  # Transient TeX outputs; source/figure PDFs and required bibliography exports remain eligible
  *.aux
  *.log
  *.fls
  *.fdb_latexmk
  *.synctex.gz
  *.toc
  *.lof
  *.lot
  *.out
  *.bcf
  *.run.xml

  ```

  Verify with `git check-ignore -v -- <actual-generated-paths>` and `git status --short --untracked-files=all`; use representative review object/request/build paths even before they exist. Review `git ls-files -- .codex-review .latex-build` and equivalent actual nested paths separately: ignore rules do not hide already tracked files. Never ignore all JSON, all PDFs, all names containing review, or whole source/figure folders to suppress noise. Untracked `U` entries in VS Code are not yet staged.
- Initial and later manual commits use an explicitly reviewed path/hunk list, not `git add .`, unscoped `git add -A`, or source globs that also traverse generated directories. `git add -A -- <reviewed-exact-paths>` remains valid for recording selected deletions as well as edits. Before committing inspect both `git diff --cached --name-status` and the staged diff; ensure the intended source set is complete and no review objects, generated PDFs/caches, secrets or unrelated changes entered it. Existing staged/tracked private artifacts require reporting exact paths and a separately authorized index-only correction; do not reset all staging, silently untrack/delete files, or rewrite/purge remote history. A normal source repository intentionally does not restore the full private review chain; use the dedicated archive when that is actually requested.
- Use meaningful, scoped commits for an authorized writing round or milestone, not every keystroke/save. Review exact diffs and stage only this task's approved files/hunks, preserving unrelated or concurrent author edits. Default research-writing checkpoints contain accepted source results only, never candidate snapshots, annotations or runtime DATA; a Git commit is not author acceptance. If scoped staging cannot preserve other edits, stop without resetting/overwriting them. First source commits use the same history-free review placeholder rather than uploading a live ledger with unavailable private objects. Default indentation needs no Git and creates no commits. The former combined formatting/commit action is retired.
- GitHub privacy is required when this optional backup is configured, not an optional suggestion. Resolve the exact owner/account and repository name; inspect any existing `origin` and the intended existing GitHub repository before creating anything. Reuse an authorized private target. A matching public repository, unrelated remote or conflicting remote history is a blocker, not permission to change visibility, replace `origin` or upload elsewhere. Before the first repository creation/upload, obtain project-specific authorization for the concrete target unless already granted. Prepare the local inventory, exclusions and commit first so this is one final, reviewable confirmation; do not repeatedly ask for the same authorized target on later pushes. Use the user's authenticated Git/CLI or supported connector without reading/printing tokens; let the user perform a required login.
- For an authorized new remote, create an empty **private** repository without an auto-generated README, license or initial GitHub `.gitignore`, so its history does not conflict with the local first commit. Link it as `origin` only if no conflicting remote exists, then push `master` and configure `origin/master` as upstream. Existing repositories retain their actual history and applicable branch policy; do not force a new initialization over them.
- Verify completion from actual results: the local repository root is the intended paper folder, the scoped first commit exists, `origin` points to the authorized owner/repository, upstream tracking is correct, the remote reports **private**, and a fresh fetch confirms the intended local/remote commit matches. Report the local path, branch, private repository link and actual synchronization state. A configured URL or successful repository creation alone is not a completed first backup. If login, target authorization, networking or a push is blocked, report **local ready / remote incomplete** and the exact remaining action; do not create a public fallback or claim both sides are initialized.
- With publication authorization, push subsequent scoped commits by ordinary fast-forward to the verified configured upstream and confirm the pushed commit on the remote. Never force-push, rewrite history, silently resolve conflicts, change visibility or substitute another remote/branch. Divergence, missing credentials or protection rejection remain explicit blockers; local writing, compilation and commits can continue offline without falsely reporting remote backup success. Saving and compiling alone do not commit or push.
- Use existing commits, branches, tags and VS Code's diff/history for review and recovery. Show the relevant revision and intended restoration scope before a content-overwriting restore; prefer a recoverable branch or a new revert commit where suitable. Do not use `reset --hard`, `clean`, delete branches or discard author work automatically. Version history and staging do not replace the numbered clean-source author-decision workflow in review-round.md. Its immutable .codex-review objects are independent of HEAD and are not carried by ordinary branch pushes; use the dedicated private review archive when needed. Preserve submitted, pre-round, accepted and candidate identities separately. No extra manuscript copies or Markdown trackers are required.
- Keep one short environment/version-control note in the existing manuscript header comments (verified engine/year, source/build roots, Git/upstream role and approved remote identity). Never store credentials, growing commit logs or a duplicate reviewer state there. Use LaTeX comments; do not imply support for another writing format.


## Manual project backup

The separate Git backup command remains available for explicitly selected ordinary sources/assets in projects without an active review ledger. If the changed TeX contains an active ledger, the editor routes to the accepted-result action below; the raw backup API rejects selecting that state owner. It does not initialize Git, create/link a remote, format source or accept proposals. Reuse an already authorized target without asking again. Additional bibliography/figure/config changes require their own explicitly approved file selection; do not fold arbitrary untracked assets into the automatic accepted-prose checkpoint.

The button requires the paper folder to be the actual Git root, master tracking origin/master, a configured author identity, an available authenticated GitHub CLI and no ongoing Git operation or existing manual staging. It fetches before checking history; remote advancement/divergence stops rather than auto-merging. Only the selected saved file snapshot is staged/committed. Existing staging or concurrent content changes stop without reset/discard. Hooks remain enabled.

Commit title uses backup(paper): plus the author's purpose. The body records purpose, actual file paths, change categories/statistics, and that backup does not imply acceptance or scientific issue closure. Do not use empty/generic messages or invent a semantic explanation from statistics. The author may identify reviewer concerns or relevant change IDs in the purpose to improve later AI/history searches.

Before an ordinary fast-forward push, verify the exact configured github.com target is private. Never change remotes/visibility, force push or upload private .codex-review objects, build outputs or credential paths. Supported paper assets include TeX/Bib/style files, figures and fonts; other files remain available through an explicitly scoped normal Git operation. Do not blanket-ignore figure PDFs. A normal source backup is not a full private review-chain archive, even if its tracked TeX still contains embedded state.

After push fetch and confirm HEAD equals origin/master. If a local commit succeeds but verification/network/push fails, preserve it and report local backup complete / remote incomplete with the actual error. No automatic rollback, retry or false success. Global tooling maintenance does not click this action on a real paper or upload it merely to test the button.

## Accepted-result checkpoints

The author has chosen: once every item in a batch has had an author disposition, commit the newly accepted results even if other items still need rework; push to the configured verified private GitHub and only then compact finished history. The trigger is an explicit 本轮审核完成/本批审完 or the **本轮审完：提交已接收成果并推送私有 GitHub** action. Do not infer that the author reviewed everything from opened cards, a quiet queue, a save or an AI's declaration. No further generic Git approval is needed for this authorized configured target. Missing project-specific remote authorization/setup remains a blocker to backup only, not to writing or review.

Use the installed local writing extension's `backup.js --finish-review` entry point, passing UTF-8 JSON through stdin:

```json
{"project":"<verified paper root>","state":"<actual relative owner.tex>","purpose":"<actual accepted changes and relevant reviewer concerns>","git":"<verified Git executable>","gh":"<authenticated GitHub CLI>","python":"<verified Python executable>"}
```

The editor action is `localLatex.finishReview`; it also supports the same workflow without a chat command. Its purpose input supplies searchable commit text, not another acceptance decision. From chat, derive the purpose from actual accepted changes; do not invent scientific completion. Resolve the installed/source-maintenance path from the current environment, never from a historical paper or template filename.

- `review_checkpoint.py plan` reads the accepted projection, not candidate text. It refuses mismatching manual edits rather than silently committing or overwriting them. It keeps writing rules/profile/local logic comments. Runtime DATA, review pointers and annotations are absent from the Git payload; the owner has only a source-only marker and next-ID counters. A source-only checkout can explicitly begin a fresh local batch without missing private objects; the new batch starts at 1/a under a fresh fixed-length internal identity. Current-batch counters survive restart and checkpoint compaction. Git restores successful source only, not dropped candidate history or old notes.
- The Git action preserves original files and manual staging, uses exact accepted blobs for the commit (not whole-file `git add`/`commit --only`), keeps hooks enabled, checks the actual committed blobs, verifies the private GitHub target and pushes normally. Unrelated local commits, changed remote targets, custom content transforms, divergence or concurrent changes block rather than trigger automatic merge/reset/force push. No newly accepted result means no empty commit or history compaction; cleanup can still resume against the existing verified successful checkpoint without another commit/push.
- A failed push retains the local commit, full review records and a bounded pending-backup identity in the sole state. Repeating the finish action resumes that exact commit, not a duplicate success commit. Only verified HEAD == origin/master permits `compact`; a changed local commit needs explicit reconciliation.
- Compaction removes eligible terminal records and past round history from live state. Pending/rework items and their complete required versions/notes remain; unresolved freshness is not declared solved. A terminal ID still required by dependencies keeps only its needed identity/metadata and Git locator, not old candidate text or closed notes. Session, owner, submission identity, active baselines, accepted projection, rules/plans and monotonic counters remain. Notes added while a push is running are not discarded.
- After the mechanical step, reconcile human-readable current-round navigation comments with the actual active IDs. Keep unresolved scientific issue/evidence mappings and author agreements; an accepted sentence does not authorize erasing its unresolved issue. Do not accumulate a second successful-result log in those comments or delete unstructured author notes by a guessed regex.
- The live owner remains in its original `.tex` and may still show as modified relative to the source-only Git snapshot. That is local runtime state, not an uncommitted accepted prose change. Use the finish action rather than whole-file staging; do not hide the owner with `.gitignore`, skip-worktree or assume-unchanged. No Git clean/smudge filters are installed implicitly.
- The author explicitly authorizes automatic cache collection after each successful accepted-result push. `finishReview` runs `cleanup` after compaction: permanently delete only regular, untracked, content-verified, unreachable object files immediately under the actual project's `.codex-review/objects`. This narrow lifecycle is already authorized and needs no per-batch cleanup question; it is not general permission to clean the workspace. No archive, move-aside directory or manifest is created. Do not delete the object directory itself, request attachments, views, build outputs, source/assets or other projects.
- Compute live references from the current authoritative state, including every pending/rework generation, note version/addressed version, accepted projection, submission identity, active round baseline and transaction intent. Validate required objects first; then preflight the complete exact deletion batch. Verify each target's type, confinement, content identity and Git-index absence again immediately before deleting only its direct-child name from its verified physical parent. State/identity changes or an error stop further deletion and report actual partial deletions. Needed or uncertain objects are never silently discarded.
- CLI mutation steps and collection share an OS writer lock covering object creation through state persistence. This prevents collection from deleting a freshly generated candidate before its state reference is saved. A busy operation fails visibly without deleting; the next finish action can resume collection against the same successful checkpoint. Direct library mutation callers must hold `Review.writer_lock()` over the mutation plus `persist`, as the CLI does. The small fixed lock file is not candidate history and is released automatically by the OS on process exit.

`record`, `compact` and `cleanup` are internal steps run by the Git orchestrator with a fresh owner SHA256. Do not call them to bypass the successful private-remote checkpoint. Cleanup preview is read-only; its applying branch deletes only the verified object-cache batch. Unrelated cleanup retains the global exact-target confirmation rules. Tool maintenance tests isolated repositories/transports only and never finalizes or cleans a real paper batch.
