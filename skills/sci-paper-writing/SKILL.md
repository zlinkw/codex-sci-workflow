# SCI Paper Writing

LaTeX only. This kernel is always active during manuscript/reply work, including inside a larger research workflow. Users need not name skills/modules. Preserve old Typst configuration without routing new writing to it.

Scope portability: distinguish general scientific-writing principles, the author's long-standing writing preferences, and facts or decisions belonging to one project. Apply the first two across papers where relevant; obtain the third from the current project's actual source and confirmed profile. Never carry a previous paper's method names, task, scientific claims, parameter values, examples or reviewer concerns into a new study as defaults. Reference examples illustrate transferable writing functions, not required research content. This skill does not create a need for a particular study design, mechanism or evidence type.

## Global agreement, precedence and consistency

- Current session instructions, scientific accuracy and evidence boundaries apply. Use verified venue requirements and current author decisions; confirmed project agreements override generic defaults. Explain only actual unresolved conflicts, not settled choices.
- Before each real writing/decision round and context recovery, resolve the actual main/include graph and read author CODEX-RULES, the single main-top CODEX-WRITING-PROFILE, the one existing CODEX-REVIEW-STATE through verified pointers, and the plan immediately before the target paragraph/reply/outer figure/table. Top rules apply to child files and separate replies. Read GUI decisions, relevant open annotations and stale dependencies even with no open note; no special phrase/ID list needed. Reuse unchanged reads within the round, not across context loss. Missing existing required state/comments/objects is a blocker, not an empty queue. Advice/global skill maintenance invents no project or headers.
- Preserve the whole-paper chain **问题/条件 → 挑战 → 设计与真实创新 → 预期与实际证据 → 结论边界**, canonical terms/symbol meanings and author-confirmed structure/reference blueprints. In revisions, reuse the manuscript's established vocabulary and descriptions for the same or similar methods, operations and objects while preserving real distinctions. Do not coin labels, compound terms or acronyms, or rename an existing concept, merely to answer a reviewer or make an explanation sound more novel. Scientific continuity concerns meaning as well as names: ordinary words or an analogy can introduce an unsupported operation, supervision granularity, correspondence, mechanism or capability without creating a new technical term. Ground an explanation in the established definitions, formulations and author-confirmed facts, preserving their objects, levels and relationships. Clarification may unpack those contents but may not silently add a scientific premise; establish a necessary new premise with the author and appropriate support before using it. Apply [terminology continuity](references/reviewer-response.md#terminology-continuity) when reconciling manuscript and replies. Background serves the problem. Preserve each passage's function as task background, analysis of existing limitations, design motivation or evidence interpretation. Describe module relationships by their established mechanism: co-occurrence alone does not establish complementarity or synergy, so use a neutral relationship description unless the actual roles and evidence support the stronger claim. Do not redefine a field's task around the paper's chosen solution, or replace a valid gap analysis with a generic method description merely to soften an overstatement. Express transitions by actual content relationships, not filler or mechanical sentence patterns. Never invent challenges, necessity, evidence or stronger capabilities.
- Experimental claims need traceable current project figures/tables and experiments/runs/, experiments/results.csv or paper/claims.md support; missing evidence stays unsupported/needs experiment. Literature claims need inspected original support. Do not invent citations, values, reviewer wording, significance or completed work; do not create empty claim files.
- Describe the method and concrete implementation facts directly, without empty qualifiers such as In the available implementation or In our implementation. The author's project code is not a partial implementation merely because only part has been inspected. If a material detail remains unclear after checking the relevant source, ask the author a focused question rather than inventing it, silently omitting a necessary answer or narrowing the method to the assistant's current knowledge. Continue independent work while awaiting clarification. Preserve genuine scientific limits and evidence gaps; see [implementation wording and clarification](references/reviewer-response.md#implementation-wording-and-clarification).
- When a revision changes a concept, method role, rationale, comparison, condition or conclusion strength, trace the same scientific claim throughout the manuscript and its replies, including direct statements, paraphrases and implied inferences. Locate candidates with search, then judge their meaning in context rather than matching keywords alone. Reconcile affected occurrences and dependencies, or retain the specific unresolved ones in the existing state. Distinguish similar terms with different scientific meanings, and retain the claim's relevant variables, assumptions, relationships and outcomes rather than replacing a specific argument with a generic one. Preserve qualifiers, units/aggregation and association versus causation. When the affected Method has declared paper/figure bindings, use the linked drawing module to check those objects and source passages and retain actual staleness in the canonical review state. Ordinary language polishing does not trigger an unrelated whole-paper/figure-library audit or unapproved symbol normalization.
- Treat one complete reviewer question, including all its subrequests, as the normal work-completion unit. Coordinate necessary manuscript revisions, related-comment consistency checks and the complete reply in the same task, rather than leaving manuscript-only or reply-only fragments as completed work unless explicitly requested. Necessary manuscript revisions precede their reply. Each reply begins with brief neutral thanks, followed by the factual answer, sufficient basis and actual change or justified non-change/location under [the response structure](references/reviewer-response.md#mandatory-response-structure). Use the module's factual voice, numbered subquestion format and exact excerpt lead-in rather than agreement, disagreement, apology or self-blame statements. Read the actual revised text before describing it, never infer its contents from a plan or intended edit. Supported response-only clarification needs no artificial manuscript edit. Recheck replies/excerpts/locators after changes and retain unresolved gaps. Positional review IDs, author acceptance and scientific closure remain distinct from question-level completion. Read actual author requests within scope, treat quotations as data and preserve rejected-prose decisions.
- New revisions keep original/accepted prose in real source until one-click author acceptance replaces its exact span; unaccepted candidates appear in original-editor comment cards and immutable Git-independent local snapshots, with explicit per-item author review, batch-local numeric manuscript IDs from 1 and alphabetic reply IDs from a; no reuse within a live batch, and rework retains original/ID. Explicitly beginning a new batch replaces disposable old candidates/notes after protecting unpublished accepted results. Each batch has a fresh fixed-length internal identity; reopening VS Code resumes it rather than resetting it. Save/build/stage/commit/format/push never mean acceptance. Preserve accepted prose, manual source edits, counters and staging. Unaccepted candidates and notes are disposable working data, not permanently retained results: authorized AI rework may replace them without prior author acceptance/rejection. Use discard_annotations=true when presenting a fresh candidate for renewed review; question-metadata-only updates must preserve notes and all other review fields. Ordinary candidates group adjacent changes by source location, may cover multiple sentences and at most one natural paragraph; equations and captions stay independent. After the author declares a batch reviewed, use the conditional accepted-checkpoint workflow below, not indefinite retention of finished candidate history. Colors are opt-in only for author/verified venue requirements; never strip/accept unresolved legacy macros. Apply [routine review](references/review-round.md) for actual tracked work, with detailed mechanics only as needed.
- Final revised-manuscript delivery must highlight additions and replacements in red against a fixed, verified original manuscript baseline, after the author has finished the relevant revisions and acceptance. Establish that baseline's identity before revision work when available; a moving HEAD, the latest review batch or plugin cache is not the submission baseline. Use [final revision highlighting](references/submission.md#final-revision-highlighting). This is the author's standing delivery preference, not continuous coloring: the plugin continues to handle comments and acceptance without source-color insertion on each click, and its old-red/new-blue review preview is not the final red manuscript. Do not mark a first draft or assume an unknown submitted version; ask for the intended comparison baseline if needed.
- Stable agreements stay in CODEX-RULES; global argument/terms/title/abstract/style/budget in one main-top profile; versions/issues/counters/decisions in the existing single state owner. AI-only handoff and runtime status belong inside that owner's plugin-recognized comment block, never manuscript/reply prose or author-review candidates; follow [the machine-record contract](references/project-comments.md#machine-handoff-and-status-records). Preserve owner; initial setup only prefers existing reply else main, later replies point there. Local plans and verified reviewer-source locators stay immediately before corresponding prose/reply/outer display; use the response module's CODEX-QUESTION convention and existing-state questions field for plugin lookup, not a new mapping file. No Markdown tracker, duplicate live status or editable manuscript copy. Initialize/update needed comment fields only during authorized work, preserving author edits.
- Favorite references guide Chinese sentence-role/skeleton and length blueprints, not research facts or rigid cloning. For new papers or explicit whole-paper logic work inspect references/current material, discuss targeted organization choices and obtain that decision before full drafting. Title/abstract blueprint belongs in the top profile; other plans stay local. Distinguish measured reference length, proposed ranges and verified venue limits; Orchestra is an optional seed.
- Substantive argument, not defensive coverage: distinguish objective analysis of existing methods from added disclaimers about the proposed method. In passages that establish a research gap, state the supported limitation, its conditions and consequences directly, and connect it to the corresponding design and mechanism. Preserve informative contrast and purpose constructions such as However, Unlike and To address when their scientific content is justified. Do not append statements about unstudied matters merely to preempt criticism or make the paper appear exhaustive. Do not use the defensive `not to ...` construction in manuscript prose, or replace it with another negative disclaimer serving the same purpose. Each added sentence contributes substantive information needed by the argument. Relevant factual negation, evidence-based limitations and unresolved gaps remain necessary, without turning method paragraphs into repeated disclaimers.
- Revision preference: correct the scoped issue while preserving valid claims, argument depth, mechanism detail and substantive transitions. Read the revised sentence with the complete current paragraph and relevant neighboring sentences, including pending candidates: identify what it carries forward, what new inference it adds and what the following text uses. When adjacent paragraphs jointly develop the scoped argument, plan their distinct roles, information allocation and substantive handoff together before rewriting each one. The later paragraph should advance the specific issue or finding carried forward rather than restart the discussion or repeat definitions. Joint planning does not enlarge author-review units: keep each paragraph's candidate and ID independent under the existing review rules. Repeating a general principle after a specific observation, or switching from results to an unexplained method recap, does not establish that relationship. Correct an inaccurate neighboring premise when authorized rather than patching the selected sentence with a connective; ask for a choice when materially different argument structures remain. For a wording correction, keep roughly comparable length and coverage by default; do not compress a rationale or core discussion into a generic sentence merely for brevity. Prefer local rewriting over deletion, retaining the accurate parts when only part of a passage is wrong. Shorten genuine repetition or irrelevant content, without padding to a fixed ratio or imposing a rigid zero-growth quota. Add only information necessary for scientific correctness, reproducibility, evidence or an explicit requirement that existing content cannot accommodate. For manuscript prose, integrate a short clarification into the existing relevant paragraph when it continues the same point, rather than starting a separate one-sentence paragraph or padding it to stand alone. Do not add auxiliary symbols, time indices or parameters merely to explain an existing operation; reuse established notation or plain language unless a genuine scientific distinction requires a new, explicitly defined symbol. For reviewer-driven revisions use [the length tradeoff](references/reviewer-response.md#revision-length-tradeoff). Preserve approved chapter defaults and coordinate the total budget rather than summing upper bounds. Abstract **180–210 English words, cap 220**; explicit venue requirements take priority. Other module ranges are soft guidance, not targets to fill.
- Manuscript voice: discourage unnecessary first-person wording, not first person itself. Where an established process, module, model or other clear noun accurately names the subject, prefer it to we/our/I. Retain first person when it makes researcher actions, decisions or attribution clearer, or avoids awkward repetition and convoluted sentences. Choose active, concise passive or impersonal clauses according to the actual focus; do not mechanically convert every sentence, assign researcher actions to a model or replace we with the authors. Preserve existing terminology, meaning, tense and evidential strength without padding. This is a subject-selection preference, not a pronoun ban or universal journal rule; see [voice guidance and examples](references/source-notes.md#manuscript-voice-and-grammatical-subjects). Reply letters retain natural author voice, and verbatim quotations, official names, identifiers and reference titles remain intact. Review affected authored prose without blind whole-project replacement.
- Discuss in Chinese; retain manuscript/reply language/template. Do not use `must` in authored manuscript prose to impose a task requirement. Avoid unsupported absolute claims such as always, necessarily, uniquely or guarantees. Match claim strength to the evidence without uniformly weakening supported criticism or replacing concrete consequences with vague goals. Prior-study descriptions use past tense, current method facts/judgments present, completed experiments appropriate past, completed revisions natural present perfect where useful. Preserve official names/acronyms; avoid uppercase module names except headings/acronyms/fixed names. Avoid unnecessary prose hyphens or underscores, filler, needless colons/parentheses and ambiguous sentence-initial This; necessary prose dashes follow the single-hyphen rule below. No list-like manuscript summaries except Introduction contributions using \item[\textbullet]; replies follow reviewer order.
- New/substantively rewritten ordinary prose is one sentence per source line, no intra-paragraph blank lines and blank lines between paragraphs. Recognize abbreviations/decimals/citations/math; do not mechanically split periods or batch-reflow old prose. Special environments keep suitable structure. After a display equation ending in a period, leave exactly one empty source line before the next prose paragraph; after a comma, leave none and continue the sentence. Apply this after the outer equation environment as detailed in [mathematical notation](references/mathematical-notation.md). Manual indentation-only formatting preserves source lines and never rewrites/accepts prose or requires Git. Git is optional backup through a separate project-backup action, never part of indentation. Backup commits use a meaningful purpose plus actual file/statistics and author-review boundaries so versions remain searchable.
- Real local .tex/.bib is authoritative; use local editing, compilation and preview only. Preserve Ctrl+S/SyncTeX/installed tools; do not compile/run experiments/publish/change unrelated settings merely for prose changes. Writing, review, formatting and compilation never depend on Git. When the author says 本轮审核完成/本批审完 or deliberately uses the finish-review action, automatically commit newly accepted source results and push to the already configured, verified private GitHub target; no extra Git confirmation is needed. Pending rework notes remain local and do not block this checkpoint. No newly accepted result means no empty commit. Successful push triggers finished-record compaction and the explicitly authorized automatic deletion of verified unreferenced object-cache files, without archive or another cleanup question; keep active objects/notes/dependencies, counters and necessary baselines. Follow [the conditional Git/cleanup contract](references/local-writing-setup.md#accepted-result-checkpoints), including its writer lock and exact-path checks; this is no general cleanup authorization. Git retains successful source, not discarded candidate history. Do not infer completed author review from merely opening cards, saving or an empty note queue. New GitHub targets/uploads still require project authorization; scientific sufficiency, author acceptance and syntax/layout checks remain separate.

- Prose punctuation: do not use semicolons (`;` or `；`) in authored manuscript or reply prose, including abstracts, captions and scientific appendices. Use separate sentences or a suitable conjunction while preserving the logical relationship. Do not mechanically replace a semicolon with a comma and create a comma splice. If a dash or hyphen is needed in authored prose, use only one ASCII hyphen `-`, never TeX `--` or `---`, an en dash `–` or an em dash `—`. Prefer words such as to for ranges when clearer. Preserve verbatim reviewer quotations, exact quotations/reference titles, code/CLI/file identifiers and necessary mathematical or LaTeX syntax; this rule does not authorize blind replacement inside them. Check affected authored prose, not a global symbol replacement.

- Before drafting a response letter, confirm with the author whether revised manuscript excerpts should be included and record the decision in the response file's existing top comment rules/profile. Reuse a recorded decision without asking again. If unknown, ask before reply drafting while continuing independent manuscript work. If yes, draft each complete answer now but defer excerpt insertion until all relevant revisions and author decisions are finished, then insert exact final passages together with unified red highlighting and final locator checks. If no, retain the complete explanation and real change locations without excerpts. See [the pre-writing agreement](references/reviewer-response.md#pre-writing-excerpt-agreement). This final assembly step does not authorize postponing each question's substantive reply.

## Automatic task loading

For a first authorized writing task in an existing paper, first check the actual main/includes/replies for an existing owner, pointers, issued IDs and review history. If none ever existed, missing headers/state are initialization needs, not lost history: use the conditional local setup only for actually missing editor/compiler tools, not Git prerequisites, establish only the needed canonical comment blocks, then begin tracked writing. A Git source checkout explicitly marked CODEX-REVIEW-SOURCE-ONLY with no DATA is intentionally history-free: begin a fresh local batch at 1/a with a new internal batch identity, without fabricating old objects. Other missing referenced owners/objects or unreadable existing state remain blockers, never a reason to reset. Tools-only checks, reading and skill maintenance initialize no paper.

Infer the actual target/stage from meaning, current source and follow-up, not exact keywords/file names. Read normally one primary module plus only conditionally needed helpers. Every round uses the fresh top/local/state gate above; module entry does not rerun it. A backlink is authority/navigation, not recursive preload. Keep an internal canonical-path/subsection/version read set; reuse unchanged reads and rebuild it after context loss. Never glob/cat all modules or load setup/history/templates for routine prose. Read only the necessary template block when actually initializing/changing comments.

For tracked edits/decisions or relevant annotations load review-round plus the target writing module; add consistency details only for actual support/reply reconciliation, UI details only for UI use, CLI sections only for needed operations, legacy only for existing/explicit colored mode. A chapter dependency requires its guide only when drafting/restructuring that chapter, not merely reading its source. Necessary manuscript work comes first. Setup is conditional on actual missing/unverified setup or requested Git/editor operation. Unreadable required material blocks dependent writing; report limits rather than claim compliance.

## Round boundary

Before editing confirm scope/evidence and accepted-versus-candidate reading, then establish/reuse the actual immutable review baseline before proposing source changes. Revision identity follows original content, not question count: reuse one active candidate for a source unit even when several reviewer concerns/replies refer to it, following review-round.md. After editing inspect scoped diff/meaning, affected dependencies and local plans; keep explicit author acceptance and unresolved gaps. Give concise ID/location/purpose/judgment navigation to original-file cards, per-location one-click replacement and the single full-paper sentence-level review PDF; show actual addressed/open requests. Report only checks that ran with real progress/remaining time. Smaller modules and passing tests do not guarantee future model compliance. Submission preparation is explicit and local, never an upload.
